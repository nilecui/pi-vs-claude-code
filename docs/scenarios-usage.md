# coms-net 控制面板 · 场景使用说明

本面板用于**观察并编排多个真实 Pi agent 的协作**。下面的「真实业务场景」都是**真实调用模型**(Codex 订阅 / MiniMax 等),不是 mock 脚本回放——会真实 spawn agent、真实发消息、真实产出。

---

## 0. 准备(只需一次)

在仓库根目录的终端里,分别起 3 个常驻服务:

```bash
# 1) 消息中枢 hub —— 必须开 firehose,否则看不到 agent↔agent 的 peer 消息
PI_COMS_NET_OBSERVER_FIREHOSE=1 just coms-net-server

# 2) 后端服务 server —— API + SQLite 持久化 + 服务端编排 + 拉起真实 agent(取代旧 spawner)
just server

# 3) 控制面板(本应用)
cd apps/coms-dashboard && bun run dev      # http://localhost:5273
```

> **编排现在跑在后端**:点「运行编排」由 server 创建一次 run、在服务端按场景的步骤 DAG 真实调用各 agent,过程经 SSE 流式推给浏览器,运行记录与装配产出落 SQLite(`apps/coms-dashboard/server/data/coms.db`)。**刷新/重开浏览器不丢**;关掉浏览器运行也会在后端继续。

模型凭证:
- **Codex 订阅(推荐,免 API key)**:先在终端 `pi` 里 `/login` 选 *ChatGPT Plus/Pro (Codex)*,即可用 `--provider openai-codex --model gpt-5.5`。
- **MiniMax**:把 `MINIMAX_API_KEY=...` 写进仓库根的 `.env`(已 gitignore)。

> 这些真实 agent 是 TUI 进程,由 spawner 在后台 tmux(PTY)里启动;**面板/浏览器无法直接拉起进程**,所以 spawner 必须在跑。

## 1. 通用流程(所有场景一致)

左栏「**真实业务场景**」区:

1. **选场景**(下拉):层级编排(演示) / 标书制作 / 合同审查。
2. **填输入**:输入框已预填一份真实示例,可直接替换粘贴你的 RFP / 合同 / 任务。
3. **▶ 一键运行**:面板经 spawner 起齐**缺失的**角色 agent(已在线的不重复拉起,避免 `tech-writer2` 堆积)→ 等它们注册(约 10–25s)→ **面板按确定性步骤逐跳分派**:把任务发给某角色、等它真实回复、再把回复喂给下一个角色,最后由 **lead** 角色整合。

> **为什么是面板驱动(确定性编排)而不是让 lead 自己分派**:实测让 lead(gpt-5.5)「自觉」用 coms 工具调下属并不可靠——它往往自己一口气把活全干了,团队不参与。改为**由面板代码驱动 fan-out**:每一跳都是「面板→角色→面板」,团队必然参与、中间产出全程可见、可复现。这也更贴合工程化落地(终止条件/重试/分支都在代码里可控)。
4. **观察过程**:
   - 中间关系图:节点=各角色 agent,边上数字=该连接消息数,**消息粒子沿边动画**;
   - 顶部 mac 终端条:每个 agent 一个 shell 小窗,**流式**显示它收发的消息;
   - 点关系图边上的数字 → 弹出该连接的**对话框**(完整往返)。
5. **📄 查看产出**:lead 把最终结论报回控制面板后,运行区出现「查看产出」按钮 → 弹窗**完整、可复制**地展示最终成果(见下「产出在哪」)。
6. **停止**:点「停止」清理本场景起的 agent(只杀本场景的,不动别的)。

### 产出在哪
最终成果 = **lead 角色报回控制面板的内容**。它会同时出现在:
- 运行区的「**📄 查看产出**」弹窗(**最适合读全文 + 一键复制**);
- lead 的终端小窗(shell 流,可点绿灯放大);
- 「lead ↔ 控制面板」那条边的对话框;
- 底部全局活动流。

## 2. 场景详解

### 2.1 层级编排(演示)— hierarchy
- **角色**:`boss`(层级根)、`lead-a`、`lead-b`。
- **输入**:给 boss 的一句任务(默认:询问两个 lead 各自最该优先解决的问题并汇总)。
- **流程**(面板驱动):面板**并行**问 lead-a / lead-b → 收齐两人回答 → 把两份回答交给 boss 汇总 → boss 产出综合结论。
- **产出**:boss 的综合结论。
- **用途**:演示「自上而下分派 / 逐级汇总」的编排骨架,也是另两个业务场景的基础形态。

### 2.2 标书制作(投标响应)— 层级 + 合规校验
- **角色**:`bid-lead`(投标负责人)、`tech-writer`(技术方案)、`commercial`(商务/资质/报价)、`compliance`(合规审查 / verifier)。
- **输入**:招标文件(RFP)要点 / 评分项 / **废标项**(预填了政务云采购示例,替换成你的真实 RFP)。
- **流程**(面板驱动,确定性):
  1. 面板把 RFP **并行**发给 tech-writer(技术章节)与 commercial(商务/资质/报价章节),各自产出草稿;
  2. 收齐两份草稿,面板交 compliance 对照**废标项与资格条件**逐条校验,回「缺失项清单 + 整改建议」;
  3. 面板把 RFP + 两份草稿 + 合规校验一并交 bid-lead 整合,产出「**标书大纲 + 废标项自检表**」(最终成果)。
- **产出**:整合后的标书大纲 + 废标项自检表(在「查看产出」里看)。
- **为什么要多 agent**:单 agent 吞整本 RFP 易丢信息;拆成聚焦角色 + **自动废标项检查**(高价值)+ writer↔compliance 迭代评审环。
- **工程化**:RFP 作输入注入;角色 prompt 可固化为 `.pi/agents/*.md` + 检索/模板技能;产出落文件;终止条件 = 合规通过或 N 轮;可挂进真实投标流水线。

### 2.3 合同审查(法务红线)— peer + 互检
- **角色**:`legal-lead`(法务负责人)、`intake`(条款提取)、`risk-reviewer`(风险审查)、`redline-drafter`(修订建议)。
- **输入**:合同文本 / 关键条款(预填了含若干风险条款的示例)。
- **流程**(面板驱动,确定性):
  1. 面板让 intake 把合同拆成结构化条款(付款/违约/知识产权/终止/保密…);
  2. 面板把条款交 risk-reviewer 对照 playbook 标注每条风险等级与理由;
  3. 面板把风险标注交 redline-drafter 出红线改法,**再交回 risk-reviewer 复核是否引入新风险**(互检);
  4. 面板把全部材料交 legal-lead 汇总「**审查意见书 + 谈判要点**」(最终成果)。
- **产出**:审查意见书 + 谈判要点(在「查看产出」里看)。
- **为什么要多 agent**:提取/评估/修订分离上下文;risk↔drafter **互检**防止「修一个风险引入另一个」;可用不同模型互检更稳。
- **工程化**:合同文本作输入;角色 prompt + playbook 作知识库/技能;产出落文件;终止条件 = 复核通过。

## 3. 其他面板能力(非场景)

- **+ 新增智能体**:表单选模型(Codex 订阅免 key / MiniMax 等)→ 「▶ 启动」经 spawner 直接拉起一个真实 agent;或「复制命令」自己在终端跑。
- **群发消息**:多选若干 agent,把同一条消息一次发给它们(控制面板 → 各 agent)。
- **节点点击**:查看 agent 详情 / 跳转其日志 / **直接发消息** / **让它去联系其他 agent(可多选)**。
- **关系图**:右上「视角」切布局(力导向/辐射/层级/树形,默认树形);右下放大/缩小/**居中适配**、**回放消息流**;左下图例(空闲/工作中/已停止/活跃连接)。
- **顶部终端条**:每个 agent 一个 mac 终端小窗;红/黄/绿 = 关闭/最小化/放大;可折叠、全部最小化⇄展示;底部把手**上下拖拽**调高、自动多行排版。

## 4. 真实 vs 演示

- 本文档的三个场景**全部真实调用模型**(spawn 真实 agent + 真实 peer 消息 + 真实产出)。
- 判断某 agent 是否真在响应:给它发消息后看其 **ctx% 是否上涨**、终端是否有回复。在线但 ctx 长期 0、队列堆积 = 该 agent 没在处理(僵尸会话,需到其终端排查或重启)。
- 真实运行会消耗对应模型的额度/费用(Codex 走 ChatGPT 订阅,MiniMax 按量计费),用完记得「停止」清理 agent。
